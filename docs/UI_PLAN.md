## 1. Нужен ли бэкенд

Да, но маленький и без своего хранилища.

Браузер не умеет читать папки на диске, а всё, что интерфейс должен показывать,
лежит в файлах: `project.yaml`, `storyboard.json`, `manifest.json`,
`resources/*.yaml`, `library/*/*.yaml`. Значит, между браузером и диском нужен
процесс, который читает файлы и отдаёт их как JSON. Во второй очереди
(запуск задач, публикация, прогресс в реальном времени) без процесса тем более
не обойтись: кто-то должен запускать конвейер и следить за манифестом.

Что этот бэкенд **не делает**: не держит своё состояние, не заводит базу
данных, не дублирует логику стадий. Он вызывает те же функции `core/`, что и
CLI (`load_project`, `load_manifest`, `load_all` приёмов, `list_resources`),
и отдаёт результат. Интерфейс — просмотрщик и пульт поверх файлов, как
записано в плане версий для V3. Единственное, что план двигает: пульт появляется
раньше V3, потому что смотреть на проекты и ресурсы удобнее в браузере уже
сейчас. Правило «файлы — единственный источник правды» не трогается.

## 3. Новая сущность — аккаунт

Сегодня у проекта есть только `channel: {name, platforms, language}` — это
описание канала для планнера, а не аккаунт на площадке. Для списка каналов
и их статистики нужен файл.

```
accounts/<id>.yaml             аккаунт на площадке
accounts/<id>/stats.jsonl      снимки статистики, append-only (план версий, V3: без БД)
accounts/<id>/videos.json      последний список роликов площадки с просмотрами/лайками
```

```yaml
id: doc_channel_youtube
network: youtube          # youtube | tiktok | instagram
handle: "@example_channel"
url: https://www.youtube.com/@example_channel
channel_id: UC…           # для yt-dlp / Data API
project: doc_channel         # обязателен; проект без аккаунтов = демо / в разработке
title: "Demo channel"
notes: ""
```

Правила:

- Аккаунт принадлежит ровно одному проекту; у проекта аккаунтов может быть
  несколько (один контент на YouTube и TikTok). Ссылка на несуществующий
  проект — ошибка загрузки, как опечатка в касте.
- Статус проекта **выводится**, не хранится: есть аккаунт → `live`, нет →
  `demo`. Это ровно определение из запроса, и его нельзя забыть обновить.
- `network` — сеть, а не формат: `PLATFORMS` в `core/project.py` перечисляет
  форматы (`youtube_shorts`, `youtube`, …), сеть их группирует
  (`youtube → [youtube, youtube_shorts]`).
- Снимок статистики: `{at, subscribers, views_total, likes_total, video_count,
  source}`. `videoforge account sync <id>` дописывает строку. Для YouTube это
  уже умеет коллектор анализатора (`intel/collectors/ytdlp.py`:
  `channel_follower_count`, просмотры/лайки по видео, без ключей). TikTok и
  Instagram — yt-dlp по возможности, иначе `sync --manual subscribers=…`;
  интерфейс честно показывает «вручную от <дата>».

CLI: `account new|list|show|sync`. Шаблон `templates/account.yaml` с
комментариями, как у остальных файлов, которые правит человек.

Про `features/` (08.09.2026). Единственная сущность, заведённая ради пульта, а
не наоборот: идеи из разговоров пропадали, а список «что уже умеем» жил только
в дизайн-заметки (приватные, не опубликованы), который человек не открывает. Один формат на два раздела: запись
не переезжает из «Планов» в «Возможности», у неё меняется `status` и
появляется `how_to_use`. Правило дисциплины — `done` без `how_to_use` и
`dropped` без причины помечаются проблемой прямо на странице.

Про `links/` (09.09.2026). Отдельная папка и отдельный раздел, а не вид записи
в `features/`: там возможности самого инструмента, здесь — чужое, на что мы
только смотрим, и смешивание превратило бы «Планы» в свалку ссылок. Поля
отвечают на два вопроса, ради которых закладка и заводится: `summary` — что
это, `why` — зачем нам; запись без `why` помечается проблемой прямо на
странице. Дата `checked` — потому что чужой сайт умирает молча, и закладка без
даты проверки со временем начинает врать.

Про библиотеку одно расхождение с запросом. Категории «переходы с кадра на
кадр» и «наложения» в библиотеке сейчас не точки решения: переходы живут в
плане монтажа (`cut | crossfade | dip_black | fade_in`), эффекты кадра — там
же (`zoom_punch | shake | flash | …`). Словарь `DECISIONS` закрыт намеренно,
новая точка заводится осознанно и требует приёмов с доказательствами.
Интерфейс показывает то, что в библиотеке есть; завести `transitions` и
`effects` как точки — отдельная задача через `/new-technique`, не часть
фронта.

## 5. API

```
GET /api/accounts                            список + последний снимок
GET /api/accounts/{id}                       аккаунт + history[] + videos[] + published[]
GET /api/projects                            список с status: live|demo
GET /api/projects/{id}                       конфиг + rules_md + ресурсы карточками + research + эпизоды
GET /api/projects/{id}/episodes/{ep}         раскадровка + манифест + каст + final
GET /api/projects/{id}/episodes/{ep}/report  HTML существующего отчёта (iframe)
GET /api/resources                           виды и счётчики
GET /api/resources/{kind}                    список (scope: global|project)
GET /api/resources/{kind}/{id}               YAML + портфолио + used_by
PATCH /api/resources/{kind}/{id}             переименование: тело {name}; id и ссылки на него не трогаются
GET /api/library                             точки решения и счётчики
GET /api/library/{decision}                  приёмы
GET /api/library/{decision}/{id}             приём
GET /api/features                            все записи + словари статусов и областей + счётчики
GET /api/features/{id}                       запись + problems
GET /api/links                               закладки + словари видов и областей + счётчики
GET /api/links/{id}                          закладка + problems
GET    /api/inbox                            входящие файлы днями (сегодня сверху)
POST   /api/inbox?name=<имя>                 загрузка: тело запроса — сам файл
DELETE /api/inbox/{день}/{имя}               убрать файл («-» вместо дня — корень)
GET /files/{root}/{path}                     медиа на чтение (`?download=1` — вложением)
```

Первая очередь — только чтение. Проекты, эпизоды и ресурсы по-прежнему
создаются опросом (`/new-project`, `/new-character`, …) и CLI: опрос —
это содержание, и переносить его в формы сейчас незачем.

### 6.1. Монтажный вид (сделано 09.09.2026)

Первое, что раздражало после паузы: ролик смотрят в плеере, а «музыка одна, а
субтитры другие» в плеере не видно — звук идёт мимо ушей, текст мимо глаз, и
чтобы их сверить, надо открывать `.ass` рядом с `.srt` и считать секунды в уме.

Ответ — вкладка «монтаж» у каждого ролика (`api/montage.py`,
`ui/src/components/Montage.tsx`): плеер сверху, под ним дорожки на ОДНОЙ шкале
времени — сцены с кадрами, текст на экране, плашки, речь по словам, слова
песни, волны звука, голоса и музыки, эффекты и звуки плана. Курсор идёт вместе
с видео, панель «сейчас» называет всё, что происходит в эту секунду.

Правило пульта при этом не нарушено: новых форматов нет, всё читается из тех
же файлов, а единственное, что появляется на диске, — кэш формы волны
`<файл>.peaks.json` (как `<клип>.motion.json` у профиля движения). Сдвиг
дорожки в интерфейсе — **линейка для глаза**: найденное число человек кладёт в
план монтажа или в скрипт сборки, пульт файлов не трогает.

### 6.2. Правки ролика из пульта (план от 09.09.2026)

Запрос человека дословно: «сделать файл к каждому видео, там расписано что
использовалось и ссылки на все, и код собирает из него видео; и в UI можно
вручную менять — замена файла, удлинение отрезка, добавить текст, — это
пишется в файл, и по кнопке скрипт быстро пересобирает».

Проработано тремя встречными проектами и девятью судьями. Выбран **паспорт +
правка существующего плана**; отвергнут «новый формат проекта монтажа» (15–23
дня, первый видимый результат на 13–19-й день, второй контракт рендера против
принципа 2).

**Главное, что вскрылось и что надо помнить.** `edit_plan.json` сегодня НЕ
описывает ролик целиком: при пустых `segments` источник кадра берётся из
раскадровки, озвучка — оттуда же (план не может ни выбрать другой файл, ни
сдвинуть, ни выключить), плашки — поле раскадровки с тремя фиксированными
позициями, произвольного текста со своим шрифтом и координатами в схеме нет.
Из шести приёмов ручной сборки `tests/t04_beat_text_edit` план выражает один.
Поэтому «один файл, из которого собирается видео» — это либо новый контракт
рендера, либо честное «часть роликов собирается скриптом». Выбрано второе.

1. **Паспорт материалов — сделано 09.09.2026.** `05_assemble/materials.json`
   для роликов мимо конвейера, `videoforge episode materials`, раздел
   «Материалы» в монтажном виде, значок «финал устарел» (входы новее готового
   файла). См. `features/video_materials.yaml`.
2. **Предохранитель перед первой записью из браузера — сделано 09.09.2026.**
   Правило про ПЕРЕЗАПИСЬ, а не про сборку: готового ролика ещё нет — битый
   план по-прежнему не останавливает работу (умолчание + громкая пометка
   «ПЛАН:», остаться без файла хуже); ролик уже собран — сборка отказывается
   (`assemble.PlanRejected`) и файл не трогает. Раньше опечатка в плане
   перезаписывала хороший `final.mp4` сборкой без правок: файл на месте,
   играет, а монтажа в нём нет. Заготовка стадии (`author: default`) под
   правило не подпадает — машинный черновик не повод терять ролик.
   Плюс `finalize` рендерит в `final.mp4.tmp.mp4` и подменяет через
   `os.replace` — оборванная пересборка больше не оставляет играбельный
   обрубок, который пульт покажет, а `publish` зальёт. Проверено тестом на
   прогоне `--only assemble`: это и есть режим кнопки.
3. **PATCH плана — сделано 09.09.2026** (`api/planedit.py`). Тело — весь план
   целиком (валидирует pydantic, никакого путевого DSL) плюс отпечаток
   прочитанного файла. Сервер собирает разрешённую правку сам — берёт план с
   диска и переносит в него только поля из `ALLOWED`, — и сверяет результат с
   присланным: разошлось, значит клиент менял запрещённое, и правка не
   принимается целиком (422). Чужая запись — 409. Проверяет ТОТ ЖЕ линт, что
   стадия (`edit.lint_with_material`): браузер не может быть более добрым
   судьёй. Починки линта возвращаются человеку списком, прежний план ложится
   рядом (`edit_plan.<отпечаток>.json`). В пульте — раздел «Правка» в монтажном
   виде: музыка (уровень, начало трека, даккинг, вкл/выкл), затухания, переход
   в каждую сцену; сдвиг, подобранный на дорожке слов песни, переносится в
   `music.start_sec` одной кнопкой. Правка меняет ПЛАН, не ролик.
4. **Кнопка «Пересобрать» — сделано 09.09.2026.** `POST /api/…/rebuild` зовёт
   `run_episode(--only assemble)` — ту же функцию, что CLI; ключи не нужны
   (сборке провайдеры не нужны вовсе). Два побочных правила, оба нужны именно
   из-за кнопки: раннер больше **не переписывает `manifest.providers`**, когда
   выбранные стадии никого не зовут (пересборка не должна затирать запись о
   том, какими моделями рисовали эпизод), и над эпизодом держится **замок**
   `.run.lock` — общий для пульта и терминала, потому что общей памяти у них
   нет; второе нажатие получает 409, а не второй ffmpeg поверх того же файла.
   Проверено живьём: правка `fade_out_sec` в браузере → запись в план →
   пересборка → `final.mp4` 797 828 → 801 331 байт, сборка вернула свои замеры.
5. **Контраст субтитров.** Единственная находка QA во всех четырёх `qa.json`:
   1.7 / 2.9 / 2.8 / 3.1 : 1 при норме 4.5. Чинится полями РЕСУРСА стиля, а не
   плана, — значит PATCH ресурса с показом «используется в N роликах» и кнопкой
   «сделать копию для проекта».
6. **Две быстрые ветки пересборки** (только с замером до/после): правка одного
   звука → ремукс без перекодирования видео (2.40 с против 14.2–19.0 с);
   односценный эпизод → без `concat`. Без графа узлов и `cache.json`: ручная
   инвалидация даёт худший возможный баг — вчерашний кадр под сегодняшним

## 7. Вторая очередь (не в этом плане, но архитектура под неё)

- **Кнопки `approve` и `run`.** API вызывает те же функции, что CLI;
  `run` — отдельный процесс `videoforge run …`, интерфейс ничего не ждёт в
  памяти.
- **Прогресс в реальном времени.** Манифест сохраняется после каждой сцены;
  бэкенд следит за `manifest.json` (watchfiles) и шлёт изменения в браузер
  через SSE. Состояние — по-прежнему файл, интерфейс его только показывает.
- **Задачи и планирование.** Файл `projects/<id>/calendar.yaml` (дата →
  эпизод → площадка) и `autopilot tick` из плана версий; планировщик ОС дёргает
  тик, интерфейс рисует календарь из файла.
- **Автопубликация.** Стадия `publish` получает YouTube Data API (первым),
  `publish.json` пополняется `video_id`; страница аккаунта связывает эпизод с
  роликом площадки по нему.
- **Статистика по расписанию.** `account sync` в планировщике ОС (t+24ч,
  t+7д, t+30д по плану версий) — снимки копятся, график становится осмысленным.

## 8. Чего не делаем

- База данных, ORM, миграции — нет. Всё, что видит интерфейс, лежит в
  файлах и читается при запросе; кэш только в памяти процесса и только по
  mtime.
- Формы создания проектов и ресурсов — нет в первой очереди: опрос в
  `/new-*` держит список вопросов, дублировать его формами рано.
- Авторизация — нет: сервер слушает `localhost`, это пульт одного человека.
- Собственный дизайн-фреймворк — нет, тёмная тема. Планировалось взять
  shadcn/ui как есть; вышло иначе — своя горстка примитивов в
  `ui/src/components/ui/primitives.tsx`, radix и cva в зависимостях нет
  (уточнено 15.09.2026)
  системная.
