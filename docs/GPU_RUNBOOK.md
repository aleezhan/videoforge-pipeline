# Своя карта: как гонять картинки и видео на RunPod

Записано 2026-09-09 по итогам Test 0–6 (07–08.09.2026, ≈$13.7 суммарно, журнал
`projects/_bench/LOG.md`). Это инструкция «как запускать», а не история; числа —
замеры, не прайс.

## Что это и когда нужно

Картинки (FLUX.2 klein 4B + LoRA персонажа) и видео (LTX-2.5 22B distilled, запас
Wan 2.2 A14B + lightx2v) считаются на арендованной карте через ComfyUI по HTTP.
Провайдеры `comfy` в `providers/comfy_http.py`, жизненный цикл пода —
`providers/runpod_pod.py` и команды `videoforge gpu up|down|status`. Hosted-видео
(Seedance, Hailuo, Kling) решением пользователя 08.09 не используется: минута
готового видео на своей карте $0.25, у hosted $3.

## Перед первым запуском

- `.env`: `RUNPOD_API_KEY` (аккаунт 1), `RUNPOD_API_KEY_BENCH` (аккаунт 2),
  `RUNPOD_API_KEY_3` (аккаунт 3, с 17.09.2026); какой брать —
  `VF_RUNPOD_KEY_VAR=RUNPOD_API_KEY_BENCH`. Баланс по API виден
  только через GraphQL (`myself.clientBalance`), REST v2 его не отдаёт.
- OpenSSH в PATH (Windows ставит его штатно): под управляется через `ssh`/`scp`.
- У персонажа проекта — блок `lora:` в YAML (`resources/characters/amir.yaml`):
  файл, триггер, база, сила. Без него художник рисует по паспорту, как раньше.

## Запуск эпизода

```
videoforge gpu up doc_channel            # под + модели + LoRA персонажа, ~6 мин, $0.07
set VF_IMAGE_PROVIDER=comfy
set VF_VIDEO_PROVIDER=comfy
set VF_LLM_PROVIDER=claude_cli
set VF_CLAUDE_CLI_MODEL=opus
set VF_VISION_CHECK=off               # claude_cli кадры не проверяет; Gemini выбран лимит
videoforge run doc_channel/<эпизод>       # ворота: script → planner → images → qa
videoforge gpu down                    # ОБЯЗАТЕЛЬНО: деньги текут, пока под жив
```

`gpu up` без проекта поднимает карту без LoRA (фотореал, пробы). `--video wan480`
или `both` докачивает Wan. Состояние — `.gpu/pod.json` (его читает провайдер),
журнал сессий с минутами и деньгами — `.gpu/sessions.csv`. `videoforge doctor`
показывает, поднят ли под. LoRA и её сила из `pod.json` входят в отпечаток
кадра: поменял веса персонажа и поднял карту заново — кадры и клипы эпизода
устарели и перерисуются (`ImageProvider.weights`, T-19); при опущенной карте
готовые кадры не трогаются, стадия пишет «входы кадров не сверялись».

## Что делает `gpu up`

1. `POST /v2/pods`: RTX PRO 4500 Blackwell 32 ГБ Secure EU-RO-1 ($0.72/ч), образ
   `runpod/comfyui:1.2.0-rc.163-comfyuiv0.30.0-cuda13.0`, диск 150 ГБ, порты
   22/tcp и 8188/http, ОЗУ не меньше 60 ГБ (`gpu.minRamPerGpu`). Ответ может
   отвалиться по таймауту — под всё равно создан, клиент ищет его по имени. На
   5xx от Cloudflare — повтор.
2. Ждёт SSH, сверяет лимит памяти контейнера (cgroup) с минимумом, заливает `videoforge/assets/gpu/comfy_setup.sh` и LoRA, запускает
   подготовку: aria2, модели klein (Comfy-Org/flux2-klein-4B, 16 ГБ), LTX-2.5
   (зеркало comfyicu/LTX-2.5: distilled int8 21.5 ГБ, Gemma-4 12B int8 15.4 ГБ,
   оба VAE, апскейлер), по флагу — Wan 2.2 fp8 + lightx2v (37 ГБ). Сеть на этих
   подах 130–400 МБ/с: весь набор за 2–4 минуты.
3. Клонирует ComfyUI **v0.34.0** рядом со старым 0.30 (LTX-2.5 появилась в 0.32),
   ставит зависимости (torch не трогает), поднимает на 8188 с `--cache-lru 8`.
4. Ждёт `/system_stats` через прокси `https://<pod>-8188.proxy.runpod.net` и пишет
   `.gpu/pod.json`. Не поднялось — под терминируется сам.

## Грабли, которые уже наступили

- **cgroup RAM 62 ГБ** при 251 на хосте: ComfyUI умирает при смене семейства
  моделей (klein → LTX) и при росте кэша выходов. Лечится `POST /free` перед
  первым вызовом провайдера и `--cache-lru 8` при старте. `--cache-none` память
  бережёт, но кадры дорожают втрое (энкодер пересчитывается на каждый вызов).
- **Лимит бывает и 30 ГБ на той же карте.** 16.09.2026 (t07_lora_motion_ref)
  одна RTX PRO 4500 пришла с `memory.max` 29 999 996 928, другая — с 62 ГБ;
  на 30 ГБ LTX-2.5 (энкодер 14.6 + трансформер 20.5 ГБ) убивается OOM на первом
  клипе. Теперь `gpu up` просит `gpu.minRamPerGpu: 60` в `POST /v2/pods`
  (`runpod_pod.MIN_RAM_GB`; фильтр размещения REST v2, ГБ на карту), а после
  SSH, до заливки setup-скрипта и моделей, читает лимит cgroup пода
  (`check_ram`): меньше 60 ГБ — под терминируется с ошибкой за минуты. Если в
  датацентре нет хоста с 60 ГБ на карту, `POST /pods` вернёт 400 «нет
  мощности» — это повод взять другой ДЦ, а не снижать порог. Проверено на
  подменённом API; на живой карте фильтр ещё не гонялся.
- **Прокси на мёртвый процесс отдаёт HTML с кодом 200 — или 404 с пустым
  телом.** До 16.09.2026 ожидание читало 404 как «ещё не готово», а
  неразобранный ответ `/queue` глотало, и клип ждал мёртвый ComfyUI больше
  11 минут к таймауту 1800 с. Теперь любой ответ `/history` и `/queue` не 200
  или не JSON — сбой опроса; сбои подряд 60 с (`comfy_http.DEAD_AFTER_S`) —
  ProviderError «ComfyUI не отвечает … процесс на поде мёртв?», стадия падает.
  Перезапущенный ComfyUI отвечает внятно, но не знает старый prompt_id —
  ловится по пустой истории и очереди, как раньше. `gpu status` пишет код
  ответа прокси.
- **Паспорт лица в промпте при LoRA** превращает «со спины» в анфас и «профиль»
  в три четверти. `image_prompt(lora_mode=True)` кладёт триггер вместо паспорта.
- **Пустой cast = никого.** Планнер пишет `[]` у пейзажей; главный герой только
  по явному `characters/<id>`.
- **Планнер раздаёт полы длиннее речи**: 381 с речи → 507 с хронометража. Пол
  сцены с речью теперь ≤ речь + хвост + 1.5 с (`audio.MAX_PAD_SEC`); сцен больше
  1.4× от просьбы — переспрос модели.
- **Под не пускает по SSH, если не передать `PUBLIC_KEY`.** RunPod кладёт в
  `~/.ssh/authorized_keys` содержимое одноимённой переменной окружения и больше
  ничего: ключ, сохранённый в настройках аккаунта, туда сам не попадает. С
  пустым `env` под поднимается, ComfyUI на прокси отвечает, а `ssh` получает
  `Permission denied (publickey,password)` — то есть подготовка падает уже после
  того, как за карту начали платить. 09.09.2026 так умерли два `gpu up` подряд
  (под сам себя терминировал, счёт — минуты, но работы ноль). Теперь
  `create_pod` шлёт `PUBLIC_KEY` из `~/.ssh/id_ed25519.pub` явно. Симптом легко
  спутать с «под ещё не готов»: сообщение `SSH не отвечает` появляется только
  через 300 с ожидания, а настоящая причина — отказ в аутентификации на первой
  же попытке.
- Диск пода 80 ГБ кончался (Test 1b) — теперь 150.
- Кэш моделей между подами не живёт: каждый `gpu up` качает 55–90 ГБ заново.
  При десятке запусков в неделю выгоден network volume (~$5/мес за 75 ГБ), при
  одном-двух — нет.

## Модели: почему эти

Аудит 08.09.2026 (`projects/_bench/MODELS_AUDIT_2026-09-08.md`, 14 агентов,
0 опровержений): LTX-2.5 — лучшая открытая i2v-модель, которая влезает в 32 ГБ и
допускает коммерческое использование (выше только MiniMax H3 с лицензией без
США/ЕС и в 2–4 раза медленнее; Wan 2.5+ только API). klein 4B ниже Z-Image и
HiDream по Elo, но на 20 промптах котят лучше слушается позы и действия, а LoRA
персонажа уже обучена. Декодер LTX — conv по умолчанию (те же кадры, −10–17%
времени; `VF_COMFY_LTX_VAE=diffusion` вернуть).

Что не решено: автоматическая проверка идентичности. Qwen3-VL 4B/8B пропускает
чужие лица 4/5, DINOv2 без дообучения — AUC 0.38. Идентичность держат LoRA, сид
и глаза человека на воротах; кандидат — дообученная голова на кропах
(`projects/_bench/out/test6/faces/`).

## IC-LoRA: управление движением и пиксельный апскейлер (21.09.2026)

`gpu up` их не ставит — после него отдельный шаг:

```
videoforge gpu up --no-klein --gpu "<карта>" --dc <центр>
uv run python tools/pod_iclora.py     # узлы Lightricks, DWPose, адаптеры; ~2.5 мин
videoforge bench run <замер>           # методы comfy_control, comfy_upscale
videoforge gpu down
```

Апскейлеры (`Lightricks/LTX-2.5-22b-IC-LoRA-Pixel-Spatial-Upscaler` ×2 и
`…LTX-2.3…` ×4) лежат на HF за воротами: лицензия принимается своим аккаунтом HF,
`HF_TOKEN` в `.env` (T-29). `tools/pod_iclora.py` кладёт токен на под файлом
`/workspace/.hf_env`; без токена апскейлеры пропускаются, остальное ставится.
`HF_API_KEY_ID/SECRET` в `.env` — ключи Higgsfield, не HF.

Замер 21.09 (`projects/_bench/pixel_upscale`, RTX PRO 6000 96 ГБ, EUR-IS-1,
$2.09/ч; L40S в Европе не было ни в одном центре, 4500 32 ГБ — только EU-RO-1):
черновик 384×704 на 8 с — 17 с; ×2 до 768×1408 на 8 с — 66–93 с; до 1152×2048
на 3 с — 54–58 с; 2K (1152×2048) на 8 с — 199–213 с без нехватки памяти; ×4 до
1280×2304 на 3 с — 85 с. Под EUR-IS-1 три минуты отвечал RUNNING без
`runtime`, потом поднялся сам — ждать, не терминировать. Скрипты для пода с CRLF bash не
разбирает («set: -: invalid option»): `.gitattributes` держит `*.sh` в LF.

### Рецепт кадра против модели: `anime_keyframe_recipe` (17.09.2026)

Владелец сделал p10 в ChatGPT одним вызовом (панель + промпт-правка, без листов
героев) и спросил, подойдём ли мы к такому кадру локально. Замер разводит рецепт и
модель на p10, p6 (там klein сломан на holdout) и p3 (контроль): klein 4B только с
панелью и с одной картинкой героя, Qwen-Image-Edit без Lightning, FLUX.2 [dev] 32B
с панелью и с картинкой героя; кадр в пропорции панели (`size: panel`), листы героев
выключаются `refs: false`. FLUX.2 dev — копия Comfy-Org без токена (оригинал BFL за
формой): модель fp8 35.5 ГБ + Mistral fp8 18 ГБ, карта от 48 ГБ.

```
VF_RUNPOD_KEY_VAR=RUNPOD_API_KEY_BENCH videoforge gpu up --video none --image-models qwen_edit,flux2_dev --gpu "NVIDIA L40S" --dc EU-NL-1 --disk 150
videoforge bench run anime_keyframe_recipe --branch klein_edit   # и так каждую ветку отдельно
videoforge gpu down
```

Прогон: L40S EU-NL-1 (ОЗУ 125 ГБ), 38 мин, $0.69; дубли $0.50. Скачивание 95 ГБ —
около 5 мин (35 ГБ за 92 с). klein 3–7 с на кадр, FLUX.2 dev 52–54 с с одной панелью
и 84–126 с с картинкой героя, Qwen без Lightning 91–99 с. L40S, L40 и RTX 6000 Ada
в тот час не было ни в EU-RO-1, ни в SE, CZ, IS, NO, CA-MTL, OC-AU.

- **Перебор карт не прерывать посреди `gpu up`.** Цикл «пробуем карту за картой»
  убили, когда очередной `POST /pods` уже создал под: процесс умер до записи
  `.gpu/pod.json`, и под остался без хозяина с тикающей ставкой. Найден через
  `GET /pods` аккаунта и доведён тем же `runpod_pod.up` с подменённым
  `create_pod`. После любого прерванного `gpu up` — смотреть поды аккаунта.
